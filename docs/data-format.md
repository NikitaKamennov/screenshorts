# Формат библиотеки и OCR

Источник текущего формата — `internal/core/`. Версия: `skrinpolka-screenshot-v1`.
[JSON Schema](../schemas/screenshot-v1.schema.json) описывает структуру, но
её автоматическая валидация при создании проекта не запускалась. Ядро читает
поля обычным JSON decoder и выполняет свои проверки размеров, имён и хешей.

## Одна запись

Новые записи получают общее читаемое основание по местному времени сохранения:

```text
ScreenShorts Pro 2026-11-16 14-00-00.png
ScreenShorts Pro 2026-11-16 14-00-00.png.json
```

JSON хранит текстовые поля отдельно от пикселей. Пример **вымышленный**;
строка SHA ниже — обозначение, а не готовый хеш реального PNG:

```json
{
  "schema": "skrinpolka-screenshot-v1",
  "id": "ScreenShorts Pro 2026-11-16 14-00-00",
  "image_file": "ScreenShorts Pro 2026-11-16 14-00-00.png",
  "created_at": "2026-11-16T10:00:00Z",
  "width": 1280,
  "height": 720,
  "metadata_revision": 1,
  "image_revision": 1,
  "note": "Настройки вымышленного сайта, раздел уведомлений",
  "tags": [],
  "ocr": {
    "status": "not_requested",
    "raw_text": "",
    "corrected_text": ""
  },
  "image_sha256": "<SHA-256 итогового PNG: 64 шестнадцатеричных знака>"
}
```

При совпадении имени в одну секунду добавляются `(2)`, `(3)` … `(1000)` перед
`.png`; проверяются оба имени пары. Поиск свободного имени ограничен, финальная
публикация через hardlink всё равно запрещает перезапись при внешней гонке.
ID совпадает с основанием имени. Чтение прежних ID из 32 строчных hex-символов
сохранено, также допускаются имена промежуточного среза с префиксом «Скринполка».
Старые файлы автоматически не переименовываются. Ядро проверяет календарную
дату и точный канонический вид имени; произвольные пути не принимаются.
Схема остаётся `skrinpolka-screenshot-v1`, её документационный pattern расширен.

- `created_at` — время добавления в библиотеку, UTC/RFC3339Nano. Исходное время
  создания импортированной картинки пока не извлекается.
- `image_sha256` относится к **байтам заново закодированного** PNG, а не к
  исходному импортированному файлу.
- `note` — пользовательская заметка, до 32 KiB в UTF-8. Картинка до 16 млн
  пикселей; размер входного и итогового PNG до 20 MiB.
- Для новых сохранений desktop ставит OCR автоматически; настройка
  `auto_index` управляет только ранним запуском в редакторе. Уже готовый
  результат используется повторно, явная отмена сохраняется. Поиск использует исправленный текст при `has_correction=true`, иначе
  исходный; хеш входа OCR должен совпадать с `image_sha256`. Визуального
  описания в формате нет.
- Список читает только пары непосредственно в выбранной папке с каноническими
  именами. Подпапки, произвольно названные PNG и картинки без JSON автоматически
  не импортируются.

## Жизненный цикл сохранения

1. Нативный диалог выбирает исходный PNG. Ядро ограничивает размер и мегапиксели
   до полного декодирования, перекодирует картинку без чужих текстовых chunks;
   цвет полностью прозрачных пикселей обнуляется.
2. Подготовленные пиксели хранятся в памяти до сохранения/отмены. Предпросмотр
   уменьшается до 1280 px по длинной стороне. Изменение исходного файла после
   предпросмотра не меняет сохраняемые пиксели.
3. После «Сохранить» редактор передаёт сведённый PNG в Go-ядро прямо из памяти.
   Ядро повторно валидирует его и создаёт новую пару в библиотеке. Исходный
   захват, операции и история undo на диск не записываются.
4. PNG и JSON сначала пишутся во временные файлы, затем публикуются без
   перезаписи через hardlink. Ошибка второго шага приводит к попытке отката PNG.
   Об успехе сообщается после сохранения пары.
5. Если OCR ещё работает, сессия получает ID и папку сохранённой записи.
   Задание продолжается, не задерживая сохранение. После успеха/ошибки меняется
   только OCR-блок и ревизия метаданных; комментарий сохраняется независимо.

Черновик и undo не пишутся в библиотеку. Для самого OCR создаются отдельные
приватные `work/ocr-*` с `input.png` и текстовым результатом; они удаляются
после остановки worker. При изменении пикселей предыдущая задача отменяется,
а её текст не переносится в новую ревизию. Аварийное завершение может оставить
временные файлы; автоматическая очистка остатков ещё требует доработки.

Временные файлы синхронизируются перед публикацией, но два имени не являются
одной транзакцией файловой системы. При аварийном завершении возможны сироты
и остатки временных файлов публикации. Они автоматически не удаляются:
показывается список предупреждений и явный импорт копии PNG без JSON.
Начальные целевые ФС — NTFS/ext4;
отсутствие поддержки hardlink даёт ошибку сохранения.

## Чтение и перенос

Из JSON не принимается произвольный путь к картинке: имя должно совпадать с ID.
Ядро работает внутри выбранной библиотеки через `os.OpenRoot`; symlink не должен
служить обходом границ. При выдаче картинки проверяются её хеш и размеры.
Повреждённая запись изолируется предупреждением и не блокирует остальные.
PNG без JSON предлагается импортировать новой копией без удаления исходника.

Новые записи имеют `metadata_revision=1` и `image_revision=1`; старые v1 без
этих полей читаются как первая ревизия. Правка комментария увеличивает только
metadata_revision, добавляет updated_at и сохраняет незнакомые расширения.
`metadata_digest` — вычисленный SHA JSON для защиты от устаревшей правки,
передаваемый в UI; внутрь sidecar это поле не записывается.

Для переноса заметок копировать **всю пару**. Сам PNG в каркасе не содержит
нашей заметки. Импорт отдельной картинки создаёт новый ID и новую заметку,
а не переносит прежний sidecar автоматически. Выбор другой папки переключает
текущий список без перемещения старой библиотеки.

SQLite, FTS и embeddings пока отсутствуют. Очередь OCR хранится только в памяти,
кроме статуса сохранённого снимка. Будущий индекс — восстанавливаемая производная.
При ручном изменении PNG прежний хеш перестаёт совпадать; выдача изображения и
присоединение OCR отклоняются. Полная сверка содержимого при обновлении списка
и наблюдение за внешними изменениями ещё относятся к этапам 7/11.

## OCR-блок v1

`raw_text` и `corrected_text` хранятся отдельно от `note`. Дополнительные поля
совместимы с ранней v1 и могут отсутствовать:

| Поле | Назначение |
| --- | --- |
| `status` | Состояние обработки, см. ниже |
| `raw_text` | Исходный UTF-8 результат движка, до 512 KiB |
| `corrected_text` | Пользовательская версия, до 512 KiB |
| `has_correction` | Использовать ручную версию, даже если она намеренно пустая |
| `input_sha256` | Хеш именно тех PNG-байтов, по которым сделан результат |
| `engine` | Сейчас `tesseract` |
| `model_revision` | Источник/ревизия языкового профиля |
| `completed_at` | UTC/RFC3339Nano завершения обработки |
| `error` | Причина недоступности/ошибки без содержимого OCR |
| `session_id` | Случайный ID процесса; отличает прерванную предыдущую сессию |

Весь JSON ограничен 1 MiB, поэтому одновременно предельные raw и corrected
с дополнительными полями могут не поместиться: такая запись явно отклоняется.
Отсутствующий `has_correction` означает false. Старый `not_implemented`
читается как историческое состояние без запущенного OCR; новые записи начинают
с `not_requested` на шаге записи пары; desktop сразу после этого ставит OCR
и записывает `queued` либо `unavailable`. `queued` публикуется до запуска
worker, чтобы поздняя запись очереди не затирала готовый результат.
Черновики могут показывать внутренний `idle`.

Основные статусы: `queued`, `running`, `ready`, `no_text`, `manual`,
`unavailable`, `error`, `cancelled`, `interrupted`. Только успешный пустой ответ
движка даёт `no_text` и подсказку: «Текст на снимке не найден. Напиши комментарий
для дальнейшего поиска по смыслу». Ошибка/ожидание не означают отсутствия текста.
Пустой `note` допустим и не блокирует сохранение.

После повторного запуска `queued/running` прежней сессии в открытой библиотеке
отмечаются как `interrupted`, без скрытого повторения. Можно явно запустить OCR
из карточки. Персистентной очереди с возобновлением всех папок пока нет.

Инструменты скрытия личного текста обязаны сначала изменить конечные пиксели,
затем удалить/пересчитать затронутые OCR, поисковые векторы и миниатюры.

Удаление фона работает над сведённым PNG текущего черновика. Его результат
сохраняется как обычный RGBA PNG, после повторной проверки и очистки RGB при
нулевой альфе; исходник/маска/undo в пару не встраиваются. Старый OCR при
применении/undo инвалидируется. Формат sidecar из-за этой операции не меняется.
Закрытый чёрной фигурой слой поверх сохранённого оригинала для этой цели
не подходит. Рабочие слои и undo не входят в распространяемый PNG/sidecar.

Миграция читает существующую v1 и не затирает неизвестные схемы. Встраивание
iTXt/XMP в PNG — будущий отдельный экспорт с понятным выбором включаемых полей.

## Проекции полки и корзина

Поле `image_bytes` в ответе Go-моста вычисляется из размера PNG на диске. Оно
не требуется для переносимой записи; ширина и высота берутся из проверяемого
sidecar. ZIP сохраняет исходные байты sidecar, не добавляя поля проекции.
Настройки `shelf` в settings.json хранят вид, сортировку, направление, дни и
плотность. Они меняются отдельной операцией, сохраняя настройки захвата и темы.

Собственная корзина `.screenshorts-trash/<token>/` содержит исходную пару и
`receipt.json` с token/ID/временем удаления. Живой список её не индексирует.
Восстановление не меняет версии и ручной текст. Подробнее: [полка](shelf.md).
