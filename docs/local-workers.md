# Локальные защищённые workers

Помимо Tesseract подготовлен CPU-worker [удаления фона](background-removal.md).
Оба используют общий слот: одновременно запускается только один защищённый
процесс обработки. Отмена/лимиты и ОС-изоляция сохраняются. Окружение фона и
модель готовятся явными сборочными/setup-скриптами, из приложения ничего не скачивается.
Полные комплекты уже включают workers. Приёмка удаления фона ещё открыта;
[фактические результаты OCR и сборок](project-status.md) указаны отдельно.

OCR Tesseract rus+eng реализован и проходил ограниченную Windows-проверку;
это не полная приёмка всех платформ и отказных сценариев.
Для каждого задания используется один тяжёлый слот. Ожидающие сохранённые
снимки не держат PNG в памяти: картинка читается из своей библиотеки перед
началом worker. Изменение текущих пикселей отменяет устаревшее задание.

Новые сохранения (обычные, тихие, импорт и восстановленная копия PNG) получают
OCR из Go-моста независимо от UI-флажка `auto_index`. Флажок теперь управляет
только ранним OCR в редакторе. Готовые актуальные результаты повторно не
распознаются, запущенная задача продолжается; ручная отмена остаётся явной.
Недоступность движка записывается в sidecar как `unavailable`, ожидающая задача —
как `queued` до запуска worker. Сохранение не ждёт результата OCR. Скорость
нового сценария не измерялась; отдельного второго «быстрого» движка нет.

## Конфигурация

Реализованный в исходниках параметр запуска — `--runtime-config /путь/к/runtime.json`.
Без него файл ищется в `config/runtime-<os>.json` рядом с бинарником.
Linux `start-local.sh` передаёт профиль из каталога исходников.

- [runtime-linux.json](../config/runtime-linux.json): `/usr/bin/tesseract` и
  `/usr/share/tesseract-ocr/5/tessdata`, языки `rus`, `eng`.
- [runtime-windows.json](../config/runtime-windows.json): Tesseract и tessdata
  в `tools/tesseract/` рядом с EXE. Сборщик пока копирует конфиг; доставка
  самого runtime относится к этапу комплектования.

В профиле явно заданы пути, read-only корни, память, потоки, timeout, модель и
ревизия. Системные Linux-модели сейчас обозначены `system-package` и управляются
пакетным менеджером; это не выдуманный SHA выпуска. При подготовке автономного
комплекта нужны закреплённые артефакты и их manifest/SHA/лицензии.

## Защита

Linux: systemd user service/cgroup v2 с MemoryHigh/MemoryMax, swap=0,
CPUQuota=200%, TasksMax=32 и RuntimeMaxSec. В том же unit перед движком
запускается внутренний режим бинарника: он читает свою `/proc/self/cgroup` и
подтверждает конечные `memory.max`, `memory.high`, `memory.swap.max`,
`cpu.max`, `pids.max`. Если контроллер не выставлен, движок не запускается.
Это отдельная от успешного вызова systemd-run проверка ограничений ядра;
см. [интерфейс cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).
Затем — bubblewrap с отдельными user/pid/net
namespaces, очищенным окружением, read-only runtime и одним каталогом задания.
Сеть и библиотека целиком не выдаются. Отмена уничтожает unit; слот не
освобождается до фактического завершения. Отказ защиты не запускает bypass.

Для начального Ubuntu/Mint-профиля нужны пакеты `tesseract-ocr`,
`tesseract-ocr-rus`, `tesseract-ocr-eng`, `bubblewrap` и пользовательский systemd.
Подготовка исходников не запускала их установку или проверку доступности.

Windows x64: AppContainer без сетевых capabilities, read-only доступ к runtime,
право записи только в отдельном private каталоге задания. Процесс создаётся
suspended с атомарным присоединением к Job Object; лимиты — память профиля,
25% CPU дерева, до 8 процессов, уничтожение дерева при закрытии Job.
Стандартные потоки уходят в NUL, не в журнал с OCR. Ограничения прочитываются
обратно до Resume. Этот код адаптирован из MIT-исходников Звукбука; его прежняя
приёмка не считается приёмкой нового приложения.

Обе платформы проверяют свободную RAM и диск до worker. Для OCR исходный
профиль — 768 MiB памяти, 2 потока, 90 секунд; сверху оставляется резерв RAM
системе. Это ограничения, а не измеренное потребление или подтверждённый
минимум ПК. При ошибке лимит автоматически не повышается.

## Текст и сохранение

Кнопка OCR распознаёт конечный PNG редактора. Результат можно исправить,
скопировать в системный буфер или сохранить TXT UTF-8 через системный диалог.
Комментарий хранится отдельно. Повторный OCR не должен незаметно затирать
подтверждённую ручную правку той же ревизии.

Автоматический режим включается явно в настройках. Новое изображение или его
изменение создаёт задание без нажатия OCR. Редактор и сохранение остаются
доступными; раннее сохранение связывает ту же работу с ID и хешем PNG.
После закрытия процесса незавершённые OCR отмечаются как `interrupted`, без
скрытого массового перезапуска. Можно явно распознать запись из её карточки.

Только успешный пустой результат — `no_text`; он предлагает необязательный
комментарий. `unavailable`, `error`, `queued`, `cancelled` — другие состояния.
PNG без текста и комментария всё равно сохраняется. Сохранение самого PNG не
откатывается из-за последующей ошибки OCR.

Приватные временные файлы удаляются после завершения процесса. При аварийном
выходе могут оставаться файлы/профили ОС; их обработка и диагностика относятся
к общей приёмке сбоев. Физическое стирание SSD и копий ОС не обещается.
